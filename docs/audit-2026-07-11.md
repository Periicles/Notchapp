# Audit NotchBar — 11 juillet 2026

État au commit `a40a269` (main). Build : ✅ `swift build` OK. Tests : ✅ 27/27 verts. Lint : configuré, CI verte.

---

## 1. Résumé exécutif

Le projet est **sain et bien tenu** pour un MVP v0.1.0 : architecture simple et testable (snapshot model), zéro dépendance externe, CI lint→build→test, packaging dmg scripté, landing page bilingue en ligne. Les fondations sont bonnes.

Les points qui méritent attention, par ordre d'impact :

1. **Bug probable de permission calendrier** : la clé `Info.plist` utilisée est obsolète pour macOS 14+ (§3.1).
2. **`.writeOnly` traité comme accès accordé** alors qu'il ne permet pas de lire les événements (§3.2).
3. **Incohérence produit/docs** : l'app affiche une icône dans la barre de menus alors que le README et la landing page affirment le contraire (§4.1).
4. **Fenêtre de fetch limitée à demain** alors que l'état `upcomingTomorrow` promet « tomorrow or later » (§3.3).
5. **Notarisation Apple** : le plus gros levier de distribution, déjà identifié comme prochaine étape.

---

## 2. Ce qui est bien (à préserver)

- **Modèle snapshot** : `computeSnapshot` statique, pur, `Equatable` → toute la logique d'état est testable sans EventKit. C'est le bon pattern.
- **Perf idle-first** : tick 1 s et shimmer 60 fps uniquement panel ouvert ; snapshots `Equatable` pour éviter les invalidations SwiftUI redondantes.
- **SPM-only, zéro dépendance** : builds reproductibles, pas de conflit `.xcodeproj`.
- **Sandbox + entitlement calendrier minimal** : bonne posture sécurité, aucun réseau.
- **Migration des préférences legacy** gérée et testée.
- **CI stricte** (lint bloquant, PR-only) et process git propre (conventional commits, branches, PRs).
- **README** complet : états, architecture, install/désinstall, contribution.

## 3. Bugs et problèmes techniques

### 3.1 ⚠️ P1 — Clé d'usage calendrier obsolète (`Info.plist`)

`Supporting/Info.plist` déclare `NSCalendarsUsageDescription`, mais l'app cible macOS 14 et appelle `requestFullAccessToEvents()`. Depuis macOS 14, cette API exige **`NSCalendarsFullAccessUsageDescription`**. Sans elle, la demande d'accès peut échouer silencieusement ou crasher selon la version d'OS.
→ Ajouter `NSCalendarsFullAccessUsageDescription` (garder l'ancienne clé ne coûte rien). À tester sur une machine vierge — c'est exactement le genre de bug invisible sur la machine de dev où l'accès est déjà accordé.

### 3.2 P1 — `.writeOnly` considéré comme accès accordé

`CalendarManager.requestAccessIfNeeded()` (CalendarManager.swift:239) retourne `.granted` pour `.fullAccess` **et** `.writeOnly`. Or `writeOnly` ne permet pas de **lire** les événements : `store.events(matching:)` retournera vide et l'app affichera « No event today » en permanence, sans message d'erreur.
→ Traiter `.writeOnly` comme insuffisant (proposer l'upgrade ou afficher un état dédié).

### 3.3 P2 — Fenêtre de fetch incohérente avec l'état `upcomingTomorrow`

`refreshEvents` ne récupère que jusqu'à la fin de demain (`startOfDay(now + 2j)`), mais le README documente `upcomingTomorrow` comme « tomorrow **or later** » et le format de countdown inclut un champ jours (`DD:HH:MM:SS`). Si le prochain événement est dans 3 jours, l'app affiche « No event today » au lieu du countdown. Le test `test_upcomingTomorrow_countdownFormat` (offset 1j2h30m) teste d'ailleurs un scénario **impossible en production** avec la fenêtre actuelle.
→ Soit élargir la fenêtre (ex. 7 jours), soit renommer l'état et retirer le champ jours. Trancher et aligner code + README + tests.

### 3.4 P2 — Pas de récupération après refus d'accès

Si l'accès calendrier est refusé au premier lancement puis accordé dans Réglages Système, l'app ne s'en rend jamais compte (bootstrap unique, `guard .granted else return`). Il faut relancer l'app. De même, `availableCalendars` n'est chargé qu'au bootstrap : un calendrier créé/supprimé ensuite n'apparaît pas dans Settings.
→ Ré-vérifier l'autorisation sur `EKEventStoreChanged` / activation, et rafraîchir `availableCalendars` dans l'observer.

### 3.5 P3 — Panel affiché sur écran externe sans notch

`ScreenHelper.preferredScreen()` retombe sur `NSScreen.main` s'il n'y a pas d'écran built-in (clamshell). La surface noire du « faux notch » (fallback 185×32) est alors dessinée en haut au centre d'un écran externe qui n'a pas de notch — un blob noir visible.
→ Décision produit : soit masquer le panel quand aucun écran à notch n'est présent, soit assumer le « notch virtuel » (certaines apps concurrentes en font une feature avec un toggle).

### 3.6 P3 — Détails mineurs

- **`startPolling`** : `guard let self else { continue }` boucle à vide si `self` est nil (le cancel en `deinit` sauve la mise, mais `return` serait correct).
- **Look-back de 8 h** : un événement de plus de 8 h en cours n'est pas détecté.
- **Polling 30 s permanent** : tourne aussi écran verrouillé / Mac en veille d'affichage. Pause via les notifications `NSWorkspace` = gain marginal mais cohérent avec la promesse « idle-first ».
- **Erreurs avalées silencieusement** : `setLaunchAtLogin` (toggle rollback muet), `requestFullAccessToEvents` (catch → denied). Aucun logging (`os.Logger`) dans l'app — au premier bug report utilisateur, aucun diagnostic possible.

## 4. Incohérences docs ↔ produit

### 4.1 ⚠️ « No menu-bar icon » est faux

`NotchBarApp.swift:9` crée une **`MenuBarExtra`** (icône `capsule.tophalf.filled`) avec Settings/Refresh/Quit. Or :
- Landing page, carte « Invisible at rest » : *« No clutter, no menu-bar icon »*
- README §Uninstall : *« It has no Dock or menu-bar icon »*

→ Trancher : soit retirer la `MenuBarExtra` (le settings orb du notch + Quit suffisent, et ça honore la promesse produit), soit corriger la doc. Vu le positionnement « invisible », retirer l'icône semble plus cohérent — mais garder un moyen de quitter/configurer si le hover casse.

### 4.2 Doublon de surface Settings

`SettingsView` est instanciée deux fois (MenuBarExtra + popover du notch), avec deux boutons Quit et deux chemins `onPreferencesChanged` identiques. Si la MenuBarExtra reste, factoriser ; si elle part, le doublon disparaît.

### 4.3 Divers

- `CFBundleShortVersionString` (0.1.0) et `CFBundleVersion` (1) codés en dur dans `Info.plist` ; `package.sh` ne les injecte pas → risque de dmg publié avec un mauvais numéro. Injecter la version depuis le tag git dans le script.
- `Info.plist` : manque `LSMinimumSystemVersion` (14.0) — Gatekeeper laisserait l'app se lancer (et crasher) sur macOS 13.
- Pas de `CLAUDE.md` projet ni de `CHANGELOG.md`.
- `.vscode/` non suivi et non ignoré → l'ajouter au `.gitignore`.

## 5. Design / UX

- **Panel de taille fixe 640×190** : les états secondaires (une ligne de texte) ouvrent le même grand panneau noir que l'état riche. Une hauteur adaptée à l'état (compact pour `emptyToday`/`noCalendar`) rendrait l'ouverture moins « vide ».
- **Accessibilité** :
  - Interaction 100 % hover → inutilisable au clavier/VoiceOver. La MenuBarExtra compense partiellement (argument pour la garder, cf. §4.1).
  - Aucun label d'accessibilité sur le contenu du panel.
  - Le shimmer 60 fps ignore `accessibilityReduceMotion` — à respecter.
- **Localisation** : la landing page est FR/EN mais l'app est anglais uniquement, avec toutes les chaînes en dur dans `CalendarManager` (les labels sont formatés dans le modèle, ce qui bloque la localisation — cf. §6). Localiser FR serait cohérent avec le public visé.
- **Message « No event today » trompeur** quand des événements existent au-delà de la fenêtre de fetch (lié à §3.3).
- **Feedback visuel au repos** : option « fine ligne de progression sous le notch au repos » = différenciateur fort, tout en restant discret (préférence désactivable).

## 6. Architecture / qualité de code

Globalement propre. Points d'amélioration :

- **`CalendarManager` mélange accès données et présentation** : les builders statiques de snapshot formatent des labels UI (`"Starts in Xm — …"`, `"%02d:%02d:%02d"`). Extraire le formatage vers une factory/`SnapshotFormatter` : sépare data/présentation et débloque la localisation. C'est le seul vrai écart de separation-of-concerns.
- **`handlePreferencesChanged` dupliqué 3×** (AppDelegate, NotchPanelController, et le callback passé aux deux SettingsView) — même corps `refreshEvents + refreshSnapshot`. Centraliser.
- **Aucun logging** : ajouter `os.Logger` (catégories : calendar, panel, prefs) — indispensable avant d'élargir la distribution.
- **`CalendarManager.swift` fait 280 lignes** (limite lint : 300) — l'extraction du formatage règle aussi ça.

## 7. Tests

**Couvert et bien couvert** : `computeSnapshot` (6 états, filtres, bornes, clamp progression, Equatable), `Preferences` (défaut, migration, persistance).

**Manques** :
- `formatDuration` > 24 h (événement très long en cours).
- Frontière minuit pour `upcomingToday`/`upcomingTomorrow` (les tests utilisent `noonToday()` — un run de CI proche de minuit pourrait donner des résultats différents ; fixer `now` de façon déterministe par rapport à `calendar.startOfDay`).
- `startingSoon` à 0 min (« Starts now »).
- Le test countdown `upcomingTomorrow` teste un cas injoignable en prod (§3.3) — à corriger avec la décision.
- Rien sur `ScreenHelper` (logique de géométrie extraite testable : calcul de tailles à partir de valeurs injectées).
- Aucun test UI/intégration du cycle hover (dur à automatiser, acceptable de s'en passer — mais le documenter comme test manuel de release).

## 8. CI / distribution

- **Notarisation Apple** (déjà planifiée) : levier n°1 — supprime la friction « Open Anyway » qui coûte des utilisateurs à chaque install. Nécessite Apple Developer Program (99 $/an), puis `notarytool submit + stapler` dans `package.sh` (les hooks sont déjà prévus en commentaire ✅).
- **Release automatisée** : aucun workflow ne construit le dmg. Ajouter un workflow déclenché sur tag `v*` : build → package → (notarize) → upload en GitHub Release. Élimine les erreurs manuelles et garantit version = tag (§4.3).
- **SwiftLint non épinglé** : `brew install swiftlint` prend la dernière version → une nouvelle règle peut casser la CI sans changement de code. Épingler la version.
- **Homebrew cask** : une fois notarisé, `brew install --cask notchbar` = canal de distribution gratuit et crédible.
- **Mise à jour in-app** : à terme, Sparkle (standard macOS indé) ou a minima un check de version GitHub Releases avec lien.
